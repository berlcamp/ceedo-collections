## What exists

**Two migrations**, both retiring deferrals Phase 3a recorded rather than adding new scope:

- `20260919000043_collections_shift_id.sql` — `collections.shift_id`, nullable, with a
  partial index. `post_collection` carries it from the payload; `close_shift` scopes its
  count and sum by it instead of by `(collector_id, business_date)`. That older scoping
  refused an honest closeout whenever a collector worked two tablets in a day or opened a
  second shift on one device — it failed safe, never silently, but it refused someone who
  had done nothing wrong.
- `20260919000044_correction_preserves_shift.sql` — spec E3.
  `resolve_exception_corrected` now re-asserts `shift_id` from the device's stored payload
  alongside `id` and `device_id`. A corrected receipt is cash that was in that collector's
  drawer during that shift; a correction that moved it would unbalance a closeout that had
  already balanced, with nothing pointing at why.

**Two new packages**, both pure TypeScript, neither importing React Native:

- `packages/db-local` — the device's Drizzle schema. 21 tables in two halves:
  `PULLED_TABLES` (17, which an epoch reset empties) and `DEVICE_AUTHORED_TABLES` (4, which
  it must never touch). A test forbids a table appearing in both, so one added later must be
  classified deliberately rather than defaulting into the wipe. Money is `text` throughout.
  Migrations are generated by `drizzle-kit` and committed.
- `packages/sync-engine` — pull, apply, cursor, epoch, reset, outbox, push, sign-in gate and
  shift lifecycle. Behind two interfaces: `SqliteDriver` and `Transport`.

**`packages/shared` additions:** `enrollment-payload.ts` (the QR/manual codec, with a
checksum) and `money.ts`'s `toDecimalString` (the outbound wire form, deliberately separate
from `format`, which is for a person).

**Three Edge Functions now validate their bodies** against a generated copy of
`sync-contract.ts` (`supabase/functions/_shared/contract.ts`, written by
`pnpm edge:contract`). A staleness test fails if the copy drifts.

**The collector app** (`apps/collector`): `enroll`, `sign-in`, `shift`, `closeout`, plus two
probes that stay — `bcrypt-probe` and `engine-probe`. They are the only things that will
catch a future Expo SDK upgrade silently unlinking the native bcrypt module or changing
`expo-sqlite`'s transaction semantics.

**One web change:** the device credential panel renders the enrollment QR client-side, from
state that already holds the secret. It is never sent anywhere to be turned into an image.

## The two measurements, and what they invalidated

**Hermes bcrypt** (`measurements/phase-3b-i-bcrypt-hermes.md`). `bcryptjs` verifies a
cost-12 hash in **22,265 ms** on the target tablet in a release build, against a 2,000 ms
threshold. Hermes has no JIT and no WebAssembly, so there is no JavaScript fix — that figure
*is* the ahead-of-time-compiled result. The remedy is `apps/collector/modules/ceedo-bcrypt`,
a local Expo module wrapping `at.favre.lib:bcrypt`, at **~482 ms — 47× faster**.

This invalidated a design assumption mid-phase and added Task 2a, which the plan did not
originally contain. Spec D3 was untouched: same cost-12 hash, same mitigation. **An
`import bcrypt from "bcryptjs"` on the sign-in path is a 22-second sign-in.**

**First-sync duration** (`measurements/phase-3b-i-first-sync.md`). Confirmed spec E9's
budget under the real 8s `statement_timeout` that `authenticator` carries.

## What the device found that Node testing did not

Spec E1 predicts this section will not be empty, and it was not. **Four bugs, none of which
more Node tests would have caught.** The last two are the ones worth dwelling on, because
they were not wrong code at all — every unit test passed and the system was still unusable
end to end.

### 1. One malformed outbox entry deadlocked the device permanently

Task 10's engine probe left a `spoiled_form` entry in the real outbox whose payload could
not satisfy `SpoiledFormPayload`. Task 5 had put contract validation in front of the Edge
Functions, so the push was refused `400 invalid_body` — **for the whole body**. The entries
stayed `in_flight`, spec E11 correctly re-pushed the same body on the next sync, and the
server correctly refused it again. Every receipt taken afterwards would have been stranded
behind an entry that could never succeed.

This is migration `0039`'s lesson arriving by a different road. That migration gave each
entry its own subtransaction so one permanently-rejectable entry could not cost the round —
but the Edge Function validates the body *before* Postgres, so `sync_push`'s per-entry
isolation never gets the chance.

Fixed on the device, where it belongs: both ends validate against the same contract, so an
entry the device cannot validate is one the server would refuse forever. It is quarantined
locally, marked `rejected` with the failing field names, and **the row is kept** (§6.3 — a
rejection never means discard the record). `packages/sync-engine/src/quarantine.test.ts`.

### 2. `openShift` defaulted its id to `crypto.randomUUID()`

`crypto` is a Node global. Neither Hermes, React Native nor Expo's winter runtime provides
one — all three were checked, not assumed. It passed every test and would have thrown the
instant a collector tapped **Open a shift**.

The engine cannot import React Native (parent spec §4), so the id is now **required** rather
than defaulted: the missing global is a type error at the call site instead of a crash in a
market. The app supplies it from `expo-crypto`.

### 3. Sign-in blamed the network for a missing facility assignment

An enrolled tablet that synced cleanly still had an empty collector list, because
`sync_pull` scopes collectors by the device's facility assignment and the device had none.
The screen derived its message from `rows.length` rather than asking `canSignIn`, and told
the person *"this tablet has not synced yet"* — a false statement about the one thing they
had just watched succeed, pointing them at the network instead of the admin screen.

`SignInBlock` gained a fifth value, `not_assigned`, told apart from `never_synced` by
`last_full_sync_date`, which every sync writes.

### 4. A tablet in that state could not be recovered from inside the app

Collectors arrive only through the pull, and every sync in the app sat behind the shift
screen — which sits behind sign-in. The only way out was re-enrolling, which needs a
credential shown once that cannot be read back. Sign-in now has its own **Sync now**.

Alongside it: the disabled **Sign in** button explained nothing. With two collectors in
scope neither is auto-selected (deliberately — picking the wrong name and typing a correct
PIN spends one of five attempts on someone else's lock counter), so a PIN typed before
tapping a name left a dead button and no explanation. It now says which half is missing.

## Where the falsification checks were run, and what they showed

Every decision the spec records as a *decision* had its test deliberately broken to confirm
the test could see the difference. Each one below was run, not assumed:

| Claim | Broken how | Result |
| --- | --- | --- |
| E7 — apply and cursor commit together | cursor advanced in its own transaction first | cursor read `99`; one test failed |
| E8 — the reset never touches device-authored state | `"outbox"` added to the wipe loop | outbox count `0`; one test failed |
| E10 — the gate tests `status = 'open'` | changed to `status <> 'closed'` | exactly one test failed, nine passed |
| E11 — `in_flight` entries are re-pushed | `pushable` restricted to `'pending'` | returned `[]`; one test failed |
| §5.1 — a records mismatch blocks | closed the shift on `mismatch` too | one test failed |
| §5.1 — a cash variance never blocks | refused to close on a non-zero variance | a **different** test failed |

The last pair is the one that matters most: the two comparisons §5.1 warns about are told
apart by the suite, not merely described apart in prose.

**One correction to the plan.** Task 8 Step 5's second half does not reproduce. It claimed
that deleting the fixture's outbox rows would make the E8 test pass vacuously; it fails
instead, because the assertion is `toEqual({ n: 1 })` — an exact count, which an empty
fixture fails just as a wiped one does. The tautology shape it warns about needs a weaker
assertion than the one written.

## Deviations from the plan, and why

- **The enrollment codec lives in `packages/shared`,** not `apps/web/lib/devices/` as the
  plan's file list had it. Both ends run it — the web encodes, the tablet decodes — and they
  are separate bundles that cannot import across each other. A copy in each would be two
  definitions of one format, free to drift, whose divergence shows up as a tablet that will
  not enrol with nothing saying why.
- **Tasks 12 and 13 share one commit.** `packages/sync-engine/src/index.ts` exports both
  `./signin` and `./shift`, so a commit carrying only the first leaves an intermediate tree
  whose typecheck fails on a missing module.
- **Task 4's test posts through `post_collection`** instead of inserting `collections` rows
  directly. The `collections_balance` trigger refuses a hand-built row with no parts, and a
  direct insert would have left the `post_collection` half of migration `0043` untested.
- **`disableHierarchicalLookup` is NOT set in `metro.config.js`.** Expo's monorepo guide
  offers it, but under pnpm's isolated layout it makes transitive dependencies unreachable —
  measured: with it on, `expo export` cannot resolve `@expo/metro-runtime` from
  expo-router's own entry file.

## Known gaps, carried forward

### There is no web UI for device or collector assignments

`device_assignments` and `collector_assignments` are not in
`apps/web/lib/admin/registry.ts`. **A tablet cannot be taken from enrolled to working
through the UI alone** — the rows have to be written by hand. This is the single largest
practical gap in the phase, and it is what produced bugs 3 and 4 above: the state was
unreachable from the admin screens, so nobody had ever seen a device in it.

`scripts/dev-wire-tablet.sql` makes this survivable in development. It is not a fix. **3b-ii
should add both resources to the admin registry**, and a reasonable argument exists for
doing it before the collection flow, since without it no tablet can be commissioned.

### The Android package identifier is still Expo's placeholder

`com.anonymous.collector`. **Must not ship.** Changing it forces a rebuild, which is why it
was deferred rather than done mid-measurement; it is cheap now and should be done before any
device leaves the office.

### The device smoke checklist is partly unrecorded

Confirmed on the tablet: the engine against `expo-sqlite` (all four probe lines, including
E7 atomicity holding through a failing apply), enrolment by QR, and sign-in reaching the
shift screen.

**Reported as exercised but not transcribed:** the Task 14 sequence — airplane-mode sign-in
latency, the five-attempt lock surviving a force-quit, the second-collector gate, the
closeout variance and its sign, the `closed_unsynced` path, and which stages were
force-quit. The checklist rows are written and waiting for the observations. **A handover
that recorded outcomes nobody transcribed would be worth less than an empty one**, so they
are left blank rather than assumed.

### `outbox.purgeAcked` is never called

The retention rule is implemented and tested (§6.4: acked entries purged after 30 days,
rejected ones kept until resolved) but nothing invokes it. It needs a caller — most
naturally on the shift screen's sync, or at app start. Nothing breaks meanwhile; the outbox
simply grows.

## Operational notes

**After every `supabase db reset`:**

```bash
psql "$DB_URL" -v label="'llejo android'" -v pin="'123456'" \
     -f scripts/dev-wire-tablet.sql
```

A reset destroys the device row, its credential and its assignments, so the tablet must also
be re-issued a credential on `/devices` and re-enrolled by QR.

**The tablet cannot reach `127.0.0.1`.** `apps/collector/.env` must carry the machine's LAN
address (`EXPO_PUBLIC_API_URL=http://<lan-ip>:54321`). Kong publishes on `0.0.0.0:54321`, so
the LAN address works. These values are inlined at bundle time: changing `.env` needs a
Metro restart, not a reload, and never reaches an already-installed app.

**Rebuild versus reload** is documented in `apps/collector/AGENTS.md`. The rule: if it ends
up in the JS bundle, reload; if it ends up in the APK, rebuild. The one that fails silently
is `modules/ceedo-bcrypt` — Fast Refresh does not reload Kotlin, and a stale build reports
the module unavailable rather than crashing.

## What Phase 3b-ii inherits

A device that enrols, signs in offline, opens a shift, closes out with a signed variance,
and survives having no signal at any point in that sequence. A shift containing **zero
receipts** — the collection flow itself is 3b-ii's subject.

Specifically not built here, and named in the plan as a deliberate omission: spec §5.2's
*"outstanding is computed, never stored"* has no task in this phase, because nothing in a
zero-receipt shift displays an outstanding balance. The rule is not in doubt —
`parity.test.ts` pins `packages/shared`'s `fifo.ts` and `charges.ts` against the SQL — but
its consumers (the lease browse and the FIFO prefix picker) are 3b-ii's.
